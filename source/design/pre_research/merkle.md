# Merkle树优化方案

## 概览

Merkle 树（或哈希树）是一种二叉（或 k-叉）树结构，其中所有叶子节点保存数据块的哈希值，所有非叶子节点保存其子节点哈希值的组合哈希，最终形成一个根哈希，用于高效验证大规模数据集的完整性。

### 一、 哈希算法层面优化

#### 1. 传统加密哈希算法
- SHA-256（比特币、以太坊早期）
  - 优点：抗碰撞性强，标准化程度高。
  - 缺点：计算速度较慢，资源消耗高。
- SHA-3/Keccak（以太坊2.0、Polkadot）
  - 优点：抗量子攻击潜力，硬件优化友好。
  - 缺点：软件实现效率略低于SHA-256。
- BLAKE3（Filecoin、部分Layer2）
  - 优点：极速计算（比SHA-256快5-10倍），支持并行化。
  - 缺点：新算法，长期安全性待验证。

#### 2. 轻量级哈希算法
- BLAKE2s（物联网设备）
  - 优点：低内存占用，适合嵌入式系统。
  - 缺点：输出较短（256位），安全性略低于SHA-256。
- xxHash（非加密场景）
  - 优点：速度极快（GB/s级别），适合非安全敏感场景（如缓存校验）。
  - 缺点：不抗碰撞，仅用于非加密Merkle树。

#### 3. 抗量子哈希算法
- SPHINCS+（后量子签名方案）
  - 优点：基于哈希的量子安全签名，可集成到Merkle树。
  - 缺点：签名尺寸大（~40KB），计算慢。
- XMSS（IETF标准化）
  - 优点：支持状态管理，适合长期安全的Merkle树。
  - 缺点：需要维护状态，不适合高频更新场景。

### 二、 存储层面优化

#### 1.1 稀疏 Merkle 树（Sparse Merkle Tree, SMT）
- 原理：Sparse Merkle 树利用“占位符”节点替代空叶子树，仅对实际存在的键值对在顶层小范围内展开完整路径，从而避免为所有空子树分配存储。
- 优势：
  - 节省存储：只存储非空路径节点，无需为空节点消耗空间。
  - 固定树高：树高为密钥空间长度（如 256 层），代码逻辑简洁且易于支持固定高度验证。
  - 高效非成员证明：可在常数个占位哈希路径下证明元素不存在，适合动态稀疏集合场景。
- 缺点：
  - 路径长度固定为密钥位数：若密钥位宽较大，验证与更新需遍历所有层，导致性能瓶颈。
  - 内存管理复杂：插入/删除时需在长路径上更新节点，若频繁操作，可能产生大量内存分配与释放开销。

#### 1.2 Merkle 前缀树（Patricia/Trie 优化）
- 原理：Patricia树结合前缀压缩与Merkle认证，将连续相同前缀路径合并为单个边，节点包含关键字位段信息，以此减少树深。
- 优势：
  - 降低树高与 I/O 次数：通过前缀压缩，使路径更短，减少读写数据库的次数。
  - 支持动态更新：对任意键插入/删除只需在局部调整路径，局部哈希更新成本相对较小。
  - 原生支持键值存储：MPT同时存储键与值，能直接为账户状态、存储树提供可验证映射。
- 缺点：
  - 节点存储开销较大：每个Trie 节点需存储多达N个子节点哈希指针（如以太坊取 16 分支），内存与磁盘占用较高。
  - 复杂的插入/删除逻辑：前缀压缩逻辑复杂。

### 三、 架构层面优化

#### 1.1 分片设计
- 方法：为降低在大规模数据集上的 Merkle 树构建延迟，可将树构建并行拆分为多段子树，分别在多线程或者分布式部署节点上并发计算哈希，最后合并子树根哈希。
- 异步 Merkle 树：在给定批量数据时，可并行处理每个数据分片生成局部 Merkle 子树，而无需在每次插入时重建整个树 。
- 优势：
  - 并行：可以充分利用多核与分布式资源缩短构建时间。
  - 低插入延迟：在大批量插入场景下，不必每次都重构整棵树，只需按批并行更新局部分片。
- 缺点：
  - 合并开销：最后需要聚合同步各子树根，处理不当可能成为瓶颈。
  - 存储碎片管理：需要额外管理各子树中间状态，以保证并发与一致性。

### 四、现有Merkle树成熟方案

#### 1. Verkle Tree
- 简介：Verkle 树使用向量承诺（vector commitments）对一组子节点进行单一承诺，从而无需在证明中列出所有兄弟节点的哈希值，只需提供一小段承诺证明即可验证父子关系。
- Verkle 树 vs. Merkle Patricia Trie（MPT）
  
| 特性           | Verkle 树                                  | Merkle 树                                  |
| :------------- | :----------------------------------------- | :----------------------------------------- |
| 证明大小       | O(commitment)（常数级，≈150 字节以内）     | O(d·hash)（d 为树高）                      |
| 验证哈希量     | 一次多项式承诺验证+少量哈希                 | d 次哈希                                   |
| 实现复杂度     | 高，需实现 KZG 或 Pedersen 向量承诺方案     | 简单，广泛支持                             |
| 网络带宽消耗   | 小，适合频繁状态更新与轻节点同步           | 大，随状态增大线性增长                     |
| 应用成熟度     | 正在以太坊等项目中测试与集成               | 广泛应用于区块链、Git 等                   |

- 优势：
  - 极小的证明体积：针对大规模状态，Proof size 可降低至 ~150 字节，较二叉 Merkle 树节省 80% 以上带宽。
  - 支持轻客户端：小证明使得 stateless clients 能在 12 秒区块时间内接收并验证状态证明，降低硬件门槛。
  - 高并行性：向量承诺天然适合并行批量验证，可借助GPU 进一步加速。
- 劣势：
  - 实现复杂度高：需要成熟的配对运算库与可信初始化流程，开发维护成本较 Merkle 树高许多。
  - Gas 成本变化：在以太坊中引入 Verkle 树需调整相关 EIP 中的存储与操作 Gas 计费，存在兼容性风险。
  - 删除与修改不友好：当前主要优化针对追加场景，对于频繁更新与删除操作，性能与实现难度均高于 Trie 结构。

#### 2. Jellyfish Merkle Tree（JMT）
- 简介：Jellyfish Merkle 树结合了 稀疏 Merkle 树（SMT） 和 前缀树（Trie） 的优势，旨在解决传统 Merkle 树在动态数据场景下的存储效率与验证性能问题。其关键特性包括：
  - 稀疏性：仅存储非空节点，节省存储空间。
  - 路径压缩：合并共同前缀，减少树的高度。
  - 高效更新：支持快速插入、删除和批量操作。
- JMT vs. 传统 Merkle Patricia Trie（MPT）

| 特性         | Jellyfish Merkle 树                                  | Merkle Patricia Trie（MPT）                          |
| :----------- | :--------------------------------------------------- | :--------------------------------------------------- |
| 编码方案     | 紧凑二进制布局                                       | RLP 编码（递归长度前缀）                              |
| 哈希算法     | SHA3-256                                             | Keccak-256                                           |
| 存储效率     | 稀疏存储，空节点不占物理空间（Sui 加了 in-memory state） | 所有节点（含空节点）需存储哈希占位符                  |
| 分支因子     | 动态调整（16/256）                                   | 固定分支（通常 16）                                  |
| 版本控制     | 原生支持版本号，便于历史查询                         | 需外部版本管理（如区块高度映射）                      |
| 写入性能     | 批量更新优化，延迟更低                               | 单路径哈希链更新，延迟较高                            |
| 适用场景     | 高吞吐动态数据（如账户状态）                         | 通用键值存储（如以太坊全局状态）                      |

- 优势：
  - 存储效率：仅存储非空节点，空位由零哈希动态填充；版本化键支持历史节点并行存储，避免数据覆盖风险。
  - 性能：增量更新，写放大与 LSM-Tree 匹配；批量写入优化 I/O。
  - 生成速度：路径长度固定为树高；范围证明支持链表化快速扫描；证明生成高效。
- 劣势：
  - 维护复杂度：验证历史状态需重构旧版本树，相较于简单 Merkle 树，需管理版本与清理。
  - 兼容性：适配性差，与链高度融合。

#### 3. Paritytech-Trie
- 简介：该库属于 Merkle Patricia Trie（MPT） 的变种，但针对Substrate 框架进行了深度优化，可称为 Substrate Merkle Patricia Trie，与以太坊的 MPT 在结构和编码上存在差异。
- ParitytechTrie vs. 传统 Merkle Patricia Trie（MPT）

| 特性         | Jellyfish Merkle 树                          | Merkle Patricia Trie（MPT）                          |
| :----------- | :------------------------------------------- | :--------------------------------------------------- |
| 编码方案     | SCALE 编码（高效二进制）                      | RLP 编码（递归长度前缀）                              |
| 哈希算法     | Blake2b（默认）                               | Keccak-256                                           |
| 存储效率     | 路径压缩+16 位子节点位图 + 内存数据库         | 所有节点（含空节点）需存储哈希占位符                  |
| 分支因子     | 动态调整（16/256）                           | 固定分支（通常 16）                                  |
| 版本控制     | 原生版本化状态根 + 自动修剪                   | 需外部版本管理（如区块高度映射）                      |
| 写入性能     | 批量更新优化，延迟更低                         | 单路径哈希链更新，延迟较高                            |
| 适用场景     | Substrate 链(如 Polkadot, Kusama）            | 通用键值存储（如以太坊全局状态）                      |

- 优势：
  - 可定制编码：默认可选 RLP、Substrate SCALE 或自定义NodeCodec，在Substrate 中常用SCALE 编码以减少解/编码成本。
  - 稀疏优化：不为所有空分支存储节点；遇到缺失子树时使用全局“默认哈希”动态填充，极大节省磁盘与缓存空间。
  - 高效增量更新：只重算受影响的叶子到根路径节点，可批量打包更新。
  - 多版本历史：各版本节点并行存储（键中含版本号），天然支持回滚读与任意历史状态证明，无需额外快照机制。
- 劣势：
  - 单节点处理串行化 ：哈希计算与节点合并按层串行执行，缺少对GPU的原生并行支持，难以在高吞吐验证场景下充分利用硬件能力。
  - 批量更新效率有限：虽支持批量写入，但批量更新内部实现依然按节点逐个哈希和序列化，整体吞吐仍受限于单线程性能。

### 五、总结

对于海量键值存储或高吞吐更新的大数据场景，Jellyfish Merkle Tree 以其子树级别的默认哈希优化、版本化存储布局和异步批量更新能力，能够显著降低 CPU、I/O 和存储成本，是比传统稀疏 Merkle 或 Patricia Trie 更优的选择。
